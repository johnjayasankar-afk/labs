## What is already done, and what is not

**DNS is done.** `johnjayasankar.com` carries a wildcard record pointing at
Vercel. Every one of the eight subdomains already resolves, and so does
`nonsense-xyz-123.johnjayasankar.com`. Nothing needs to be added to DNS.

**Vercel is not done.** All eight subdomains answer with:

```
HTTP/2 404
server: Vercel
x-vercel-error: DEPLOYMENT_NOT_FOUND
```

The wildcard gets the request to Vercel; no Vercel project has claimed those
hostnames, so Vercel has nothing to route them to. Adding a domain to a project
is an account action. It cannot be done from a repository.

## The switch

Both repositories route every product link through one function:

```python
PRODUCT_SUBDOMAINS = os.environ.get('PRODUCT_SUBDOMAINS') == '1'

def product_url(key):
    if PRODUCT_SUBDOMAINS:
        return 'https://%s.%s/' % (key, PRODUCT_DOMAIN)
    return PRODUCT_HOSTS[key]
```

Portfolio: `tools/data_pages.py`, used by `data_systems_b.py`.
Labs: `tools/data.py`, which also generates `vercel.json`'s eight redirects.

It is **off**, and it is off on purpose. Verified by building both sites with
`PRODUCT_SUBDOMAINS=1`: 38 product links on the portfolio and all 8 Labs
redirects move to the subdomains, and no Vercel hostname is left behind. Turning
it on today would replace every working product link on both sites with a 404.

## 307 or 301 on the Labs short links

Labs redirects `/ridelens`, `/daylight`, `/raildrop`, `/gridiron`, `/agentfit`,
`/cartonry`, `/keepfloor` and `/pricing` to the products. All eight are 307
today, verified live on 25 September 2026.

**Keep 307 while the destination is a Vercel hostname.** A 301 is cached by
browsers for a long time and in practice cannot be taken back. Pointing a
permanent redirect at a name Vercel generated, and that changes if a project is
renamed or replaced, would hard-wire an address nobody controls into other
people's browsers.

**Move to 301 once the destination is a subdomain**, at step 3 above. The
argument that justified 307 was that the destination might move. Once the
destination is `gridiron.johnjayasankar.com`, it does not move: if the
deployment behind it changes, the subdomain absorbs that and the short link
never notices. At that point the 307 is buying nothing and costing a hop, a
revalidation on every visit, and the Labs origin staying in the chain.

Both states are already expressible: `permanent` in the redirect entries that
`tools/data.py` generates.

## What this does not fix

The subdomains do not change whether a product can be shown inside an iframe on
the portfolio. That is `X-Frame-Options` and CSP `frame-ancestors` on the
product, and it is a separate problem. See **Framing** below.

## Framing

The portfolio embeds products live in their case studies. An embed only renders
if the product allows this origin to frame it, and the embedding page cannot
tell a blocked frame from a loaded one: both fire `load`, and everything else
about a cross-origin frame is opaque to the parent by design.

### How the page handles it now

Every preview ships as a still, in the browser chrome the embed already draws,
with a caption that says it is a picture. The frame sits behind the still, marked
`inert`, and comes forward only when the product posts `embed:ready`. A frame the
browser refused never sends that, because its scripts never run. So the failure
mode is a labelled screenshot rather than a black rectangle under a caption
promising a working app, and that holds with JavaScript off as well.

The handshake is posted by the product, to the framing origin only, and the
browser stamps the origin on the message, so the page inside the frame cannot
claim to be somewhere else. `shared/embed.ts` in Gridiron and `src/lib/embed.ts`
in RideLens and RailDrop hold the allowlist and the sender.

One trap, found by testing it rather than reasoning about it: the handshake must
not be sent from a `requestAnimationFrame` callback. A cross-origin frame the
page has not revealed yet is occluded, Chrome defers its animation frames until
it is revealed, and the page is waiting for the message before revealing it.
That deadlocks. Send it as soon as the app has rendered instead: running at all
is the signal.

### What each product sends, in its repository

Fixed 25 September 2026, in the product repositories. **Not deployed**, so the
live hostnames still refuse.

| Product | Before | Now, in the repository |
|---|---|---|
| Gridiron | `frame-ancestors 'none'` + `X-Frame-Options: SAMEORIGIN` | `frame-ancestors 'self' https://johnjayasankar.com https://labs.johnjayasankar.com`, no XFO |
| RideLens | report-only `frame-ancestors 'none'` + `X-Frame-Options: SAMEORIGIN` | same allowlist, as its own **enforced** policy, no XFO |
| RailDrop | `X-Frame-Options: SAMEORIGIN` in the repo, not yet deployed | same allowlist, as its own enforced policy, no XFO |

Two details that matter:

**RideLens and RailDrop ship their main CSP report-only.** A report-only policy
blocks nothing and, importantly, does not override `X-Frame-Options`. So the
framing rule goes out as a second, enforced, single-directive policy, and the
`X-Frame-Options` header is removed. Leaving a `SAMEORIGIN` there would have
blocked the frame on its own whatever the CSP said, which is exactly what was
happening to RideLens.

**RailDrop was a live deployment behind its own repository.** The repo already
set `X-Frame-Options: SAMEORIGIN`; the deployment did not. The RailDrop preview
worked only because the deploy was stale, and the next RailDrop deploy would
have taken it out silently.

In development each product also accepts a loopback framer, so the embed can be
driven against a portfolio running on this machine. `process.env.NODE_ENV` and
Vite's dev server keep that out of every deployed build.
